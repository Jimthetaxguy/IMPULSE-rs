## 1. The Value of Personalization in Large Language Model Responses (fradkin-personalized-routing-loop168): partial fit at most, evaluation and prompt side only; per-user routing is no fit for the picker

This row asks `decide_step_model` to score routes on the caller's wants for the task, and to test a preference preamble before adding a router. A preference preamble is prompt text sent with the default model. That is not an input to `decide_step_model` (`impulse-rs/src/agent/step_model.rs:120` on main 921f5c9). The picker names one model per chat step. It reads `latest_verification` and `review_state` only to stay on the current model or move to `escalate_model` after a verifier failure (`HarnessStepContext` at `step_model.rs:23-33`, `escalate_model` at line 32). It does not read user tastes, prompt content, or a preamble.

A preference preamble on the default model can be tested before any per-user router, and that test belongs on the evaluation and prompt side, not in the picker. The filed mechanism already says a preference preamble on the default model does about as well as personalized routing; that is the author's claim, not a result checked here. The test itself is an evaluation arm in `selector_baselines`: the same default model, with versus without the preamble. The `Run` fixture (`impulse-rs/impulse-step-model/examples/selector_baselines.rs:23`, identical on main 921f5c9) already stores `policy`, `pass`, `cost_usd`, and `latency_ms`, so a new policy label can record those two arms. The preamble text would be written and applied on the Ion or prompt side. Putting a taste-based or per-user router inside `decide_step_model` would take the picker out of lane. The picker stays a thin, deterministic name choice, not a learned router, not a content router, and not a per-user router.

This does not merge with (a) the rounds field, (b) the cheapest-within-margin report with a Wilson lower bound and a Vernier resolution check, (c) cost logging on each pick, or (d) a harness or effort field next to each pick. A preamble arm would be a companion policy on the later baseline records, not one of those work items. It stays held for Jim behind the open selector_baselines branch.

## 2. Progress-Aware Distillation for Mitigating Stagnation in Small Language Model Agents (2610.19439): partial fit as a harness-state signal; detection already trips the loop, and does not escalate the model

This row asks `decide_step_model` to use a repeated-action detector as the trigger to move a small-model step to a larger model. The arXiv abstract describes a training-time distillation method, not a runtime router. Distilled small models get stuck in unproductive loops with persistent failed strategies. Progress-Aware Distillation (ProD) detects and penalizes that stagnation in student-generated trajectories, encodes the gap between student and teacher into an adaptive margin, and applies the penalty alongside supervised fine-tuning. The abstract reports this across eight small models from 0.6B to 8B. Those figures were not reproduced. The Impulse mapping is the register's practical use case, not the method the paper proposes.

A repeated-action detector is a harness-state signal, and that is the kind of input the picker may read. Impulse already has such a detector, but it stops the loop; it does not change the model. `ION_DEFAULT_REPEATED_CALL_STREAK` is 3 (`impulse-rs/src/loop_contract.rs:34` on main 921f5c9). `LoopBudget::max_repeated_call_streak` (line 100) is set in `ion_default` (line 131) and is disabled for the governed Builder budget (line 154). `LoopContract` (line 212) for the Ion tool loop (`ion_tool_loop` at line 235) trips on `LoopTrip::RepeatedCall` (line 299) when the same tool name and input repeat, and on `LoopTrip::RepeatedRound` (line 303) when the same batch of calls repeats across rounds. A trip opens the breaker and the loop must stop. The picker does not read these trips.

`decide_step_model` (`step_model.rs:120`) escalates only with reason `AfterVerifierFailure` when `escalate_model` is set. `StepModelReason` has only `Configured` and `AfterVerifierFailure` (`impulse-rs/impulse-step-model/src/lib.rs:99-101` on main 921f5c9). Policy v0 ignores tool-round volume (`lib.rs:122-123`; the Impulse wrapper says cost is unused in v0 at `step_model.rs:118`). If a later change used a repeated-action signal to move a small-model step to a larger model, detection would stay in the harness or Ion loop, where it already lives, and the picker would only read a boolean or a count. It could then gain a new reason beside `AfterVerifierFailure`. Using a trip to escalate instead of only stopping the loop is a policy change, not something this paper measures, and it stays held.

The streak or count, if recorded, would sit next to held item (a), a rounds field, and held item (c), cost logged on each pick. Cost belongs on `StepModelRecord` (`step_model.rs:38`); a rounds field is the held companion on the `selector_baselines` `Run` fixture, which has no rounds field today (line 23). The live record is logged only through `tracing::info!` (`step_model.rs:155`); the comment at lines 35-36 says durable ledger attachment is later work. There is no cost field on `StepModelRecord` today. These would be companion fields on the later durable log and baseline records, not a merge of those work items. This does not merge with (b) the cheapest-within-margin report or (d) a harness or effort field next to each pick.
