## 1. Partial Routing (2611.33402): partial fit, evaluation only; cost logging is a prerequisite, not the same work

The picker does not consult a quality or cost table: `decide_step_model` (`impulse-rs/src/agent/step_model.rs:120`) returns the configured model, or `escalate_model` after a verifier failure, and "Cost is unused in v0" (`step_model.rs:118`). Building a per-subtask table and choosing each step's model from it would make the picker a table-driven router, which stays out of lane. The "let the lead delegate" half is the same Ion gap as Delegent in the Loop 162 note: the picker names one model per chat step, and there is no per-subtask delegation point.

On the evaluation side, a per-subtask quality and cost table belongs in `selector_baselines`. Today `Run` (`impulse-rs/impulse-step-model/examples/selector_baselines.rs:23`) scores whole runs (pass, cost_usd, latency_ms) with a task-level `category`, and `choose-at-start` already picks a per-category best fixed model. There is no subtask field and no per-step row. Per-step data exists only as `StepModelRecord` (`step_model.rs:38`), logged through `tracing::info!` at `step_model.rs:155`, with no cost field and no durable store. Logging cost on each pick (held item) would feed such a table later, but the table also needs a subtask label and a report; it is not the same work as cost logging, the rounds field, or the cheapest-within-margin report.

## 2. MeterRouter (2611.34327): partial fit, logging half only; a hard per-query budget is a gateway and stays out of lane

Giving `decide_step_model` a per-query dollar budget as a hard input is a gateway feature, as with the Runway row in the Loop 163 note, and stays out of lane. The picker has no cost or budget input (`step_model.rs:118`). Existing loop caps are wall-clock, round count, and context size (`LoopContract` in `impulse-rs/src/loop_contract.rs`, applied from `llm_backends/mod.rs`), not dollars, and they trip the tool loop rather than choose a model. The learned graph-building half (imitation, then a GRPO variant) is also out of lane.

The logging half partly exists: each pick already returns `StepModelDecision {model, reason}` and logs `StepModelRecord`, but cost is not recorded next to the pick. That half merges with the held item of logging cost on each pick in `StepModelRecord`. It does not merge with the rounds field or the cheapest-within-margin report.

## 3. RAP and RouteabilityBench (2611.34825): partial fit, evaluation only; a new diagnostic, not a merge with the held items

This is a pre-check to run in `selector_baselines` before any router is tuned, not a change to `decide_step_model`. The example already compares the current selector to a single best fixed model (`best_fixed` at `selector_baselines.rs:74`) and to a per-category best fixed model (`choose-at-start`). It does not report whether the pool models disagree on the same Impulse tasks, or the gap between an oracle (best model per task) and that single best fixed model. Those two numbers are the Impulse-sized routeability check: if the models rarely disagree, or the oracle barely beats the best fixed model, there is little to route. This does not merge with the rounds field, the cheapest-within-margin report, or cost logging on each pick.

## 4. Latent-in-the-Middle (2611.34278), Impulse half: no fit; no cache is shared across models

Impulse does not transfer a KV cache, or any other latent state, from one model to another. A search of `impulse-rs/src`, `ion_repl`, and `llm_backends` found no cross-model cache, mapper, or shared KV path. The one cache that exists is Anthropic's same-request prompt cache: an ephemeral `cache_control` breakpoint on the system-and-tools prefix (`impulse-rs/src/llm_backends/anthropic.rs`, `DEFAULT_CACHE_SYSTEM_AND_TOOLS` at line 488, documented at lines 537-549). The tool loop may later send that same prefix to a different `ChatRequest.model` after escalation (`llm_backends/mod.rs:837`), but Impulse itself does not copy or map a cache between models. There is nothing in the current picker or backends to treat as untrusted cross-model cache input. If a shared or transferred cache is added later, that input should be treated as untrusted. This does not merge with the held evaluation items. The ROSA half is left to Grokky.
